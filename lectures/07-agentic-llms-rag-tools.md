## Коротко о лекции

До этой лекции LLM в курсе жила «сама по себе»: её предобучали, выравнивали, учили рассуждать, но отвечала она только из того, что запомнила при обучении. Седьмая лекция — о том, как связать модель с внешним миром. Первая половина (Afshine) посвящена RAG: почему нельзя просто дообучить модель или положить всё в контекст; как устроена knowledge base из chunks и embeddings; как работает двухэтапный retrieval — быстрый candidate retrieval через bi-encoder и cosine similarity, затем точный re-ranking через cross-encoder; какие есть дополнения (BM25 и гибридный поиск, HyDE, contextual retrieval, prompt caching) и как измерять качество retriever'а (NDCG, MRR, precision@k, recall@k, бенчмарк MTEB).

Вторая половина (Shervine) — о действиях. Tool calling / function calling: модель видит только сигнатуру и документацию функции, предсказывает аргументы, внешний код выполняет вызов, а результат возвращается модели для ответа на естественном языке. Разбирается, как этому учить (два типа SFT-пар) и как обойтись без SFT — подробной инструкцией в промпте, которую итеративно дорабатывает reasoning-модель по результатам на eval-наборе. Дальше масштабирование: tool selection (router), стандартизация через MCP и, наконец, агенты как цикл observe → plan → act по мотивам ReAct, протокол Agent2Agent для общения агентов между собой и безопасность (data exfiltration, защита при обучении и на inference, Agent-SafetyBench, свежий отчёт Anthropic о кибератаке).

Ключевые идеи: (1) знание модели ограничено датой cutoff, и правильный способ его расширять — добавлять в промпт только *релевантную* информацию; (2) retrieval — это два этапа с разными бюджетами вычислений: грубый и дешёвый отбор на recall, затем дорогое ранжирование; (3) при tool calling модель предсказывает аргументы, а не исполняет код; (4) агент отличается от инструмента циклом и рассуждением между вызовами; (5) с новыми возможностями приходят новые риски, поэтому начинать нужно с маленьких проверяемых сценариев на самой сильной модели.

## 1. Введение

⏱ 00:00–06:38 · [▶ смотреть на YouTube](https://youtu.be/h-7S6HNq0Vg?t=0)

Afshine открывает лекцию: тема — практические приёмы, позволяющие LLM взаимодействовать с внешним миром и другими системами. До сих пор модель была «сама по себе»: её обучили, научили рассуждать над математикой и кодом, и теперь её нужно встроить в контекст других систем. Три темы дня: RAG, tool calling и агенты.

### Повторение лекции 6

- Reasoning-модели против «ванильных» LLM: раньше промпт → сразу ответ; если дать модели порассуждать перед ответом, качество на задачах типа математики и кода растёт. Reasoning-модель выдаёт цепочку рассуждений (обычно скрытую от пользователя) и затем ответ.
- GRPO (Group Relative Policy Optimization) — ключевой RL-алгоритм прошлой лекции. Главное отличие от ранее виденных алгоритмов: он не обучает value function. Для одного запроса генерируется группа completions, считаются их награды, и advantage каждого выхода вычисляется относительно остальных наград группы.
- Награды подбирают за две вещи: за наличие цепочки рассуждений и за хороший ответ. С ходом RL-обучения растёт качество на задачах вроде AIME (сложные математические задачи).
- Побочный эффект — length bias: ответы становятся всё длиннее, даже когда качество уже вышло на плато. Причина в формулировке loss GRPO: вклад токена зависит от того, в коротком или длинном ответе он стоит. Способы смягчения из недавних статей: DAPO (нормировочный множитель, не зависящий от положения токена) и «GRPO Done Right» (нормировка просто убрана).

### Что будет в этой лекции

В прошлый раз боролись с ограниченностью рассуждений ванильной LLM. Сейчас — две другие слабости: (1) как подключить модель к постоянно меняющейся базе знаний и дать ей доступ к свежей информации; (2) как с помощью LLM выполнять действия — это часть Shervine про tool calling и агентные workflow.

## 2. Обзор RAG

⏱ 06:38–27:39 · [▶ смотреть на YouTube](https://youtu.be/h-7S6HNq0Vg?t=398)

### Проблема: knowledge cutoff

Модель обучена на данных месячной давности, а вы спрашиваете её о выборах, прошедших две недели назад. Она либо не ответит, либо ответит неверно — у неё нет связи с внешними источниками, только то, что усвоено при обучении. У всех моделей в model card указана дата knowledge cutoff; у GPT-5 это 30 сентября 2024 ([07:28](https://youtu.be/h-7S6HNq0Vg?t=448)).

Почему не дообучать модель на новых данных ([08:30](https://youtu.be/h-7S6HNq0Vg?t=510))?
- Менять знания LLM, не вызвав регрессий в другом, очень сложно — такой задачи стараются избегать.
- Непрактично: если от базовой модели сделано несколько fine-tune'ов под разные use cases, обновлять веса придётся во всех — большой overhead и сопровождение.

Почему не положить всё новое в промпт ([09:23](https://youtu.be/h-7S6HNq0Vg?t=563))? Три причины, каждой достаточно самой по себе:

1. **Контекст ограничен.** Порядок величины — сотни тысяч токенов; при прикидке «1 токен ≈ 4 символа» это сотни страниц, большая книга. Много, но для наивного подхода мало. У GPT-5 контекстное окно — 400 000 токенов.
2. **Нерелевантный контекст портит ответы** ([11:15](https://youtu.be/h-7S6HNq0Vg?t=675)). Даже при бесконечном контексте: если закидать модель посторонней информацией, она путается. Это измеряют тестом needle in a haystack («иголка в стоге сена»): в длинный промпт прячут факт и спрашивают о нём. На слайде — heatmap для GPT-4 одно-двухлетней давности: по оси x длина промпта, по оси y глубина, на которой спрятан факт. Начиная с некоторой длины модель перестаёт находить факт, особенно когда он лежит в первой половине промпта.
3. **Деньги** ([14:07](https://youtu.be/h-7S6HNq0Vg?t=847)). Оплата по токенам: чем длиннее вход, тем дороже. Для GPT-5 порядок — около $1 за миллион токенов; немного, но на всех запросах накапливается.

| Подход | Проблема по лекции |
|---|---|
| Дообучить модель на новых данных | Регрессии в других навыках; переобучать каждый fine-tune |
| Положить всё в контекст | Лимит контекста; деградация needle-in-a-haystack; цена за токены |
| RAG | Добавить в промпт только релевантное — тема лекции |

> 💡 **Дополнение — что изменилось с тех пор:** Аргумент «контекст ограничен» слабеет: у части моделей окно уже порядка миллиона токенов, и для небольшой базы (десятки документов) проще положить в промпт всё и не строить retrieval. Но два других аргумента никуда не делись: с ростом промпта растут цена и задержка каждого запроса, а качество ответов на «утопленные» в шуме факты по-прежнему падает. На практике RAG нужен ещё и там, где у разных пользователей разные права доступа к документам, и где база меняется чаще, чем вы готовы пересобирать промпт. Разумный ориентир: начинать с длинного контекста, а RAG добавлять, когда база перестаёт помещаться или дорожает.

### Идея RAG

RAG — Retrieval Augmented Generation: промпт дополняется *релевантной* информацией, и слово «релевантной» — суть метода ([15:13](https://youtu.be/h-7S6HNq0Vg?t=913)). Три шага ([16:11](https://youtu.be/h-7S6HNq0Vg?t=971)):

1. **Retrieve** — по промпту найти в knowledge base подходящие документы.
2. **Augment** — вставить найденное в промпт. На примере выборов: вопрос «кто победил?» превращается в «кто победил? — кстати, выборы прошли тогда-то, и победил такой-то». По сути, ответ подаётся в самом промпте.
3. **Generate** — отдать дополненный промпт модели и получить ответ.

**Вопрос из зала ([17:59](https://youtu.be/h-7S6HNq0Vg?t=1079)):** а если retrieval отработает плохо? — **Ответ:** именно поэтому retrieval — самое важное звено; когда говорят о RAG, в основном занимаются качеством retrieval и тем, как его оценивать.

### Knowledge base: chunks и embeddings

Сначала собирают документы, которые могут пригодиться, и режут их на chunks (фрагменты) — куски документа ограниченной длины в токенах, обычно сотни токенов. Для каждого chunk считают embedding ([19:48](https://youtu.be/h-7S6HNq0Vg?t=1188)). Тезис лектора: слышите «retrieval» — думайте «embeddings».

Три гиперпараметра knowledge base ([20:46](https://youtu.be/h-7S6HNq0Vg?t=1246)):

| Гиперпараметр | Компромисс | Типичное значение |
|---|---|---|
| Размер embedding | Больше — лучше для сложных, нюансированных документов, но больше памяти и вычислений на inference | Порядка тысяч, например 1 500 |
| Размер chunk | Слишком мал — текст вырван из контекста; слишком велик — embedding перестаёт осмысленно представлять содержимое | Около 500 токенов |
| Перекрытие chunks | Наивная нарезка без перекрытия теряет связь с предыдущим куском, нужным для понимания текущего | Низкие сотни токенов |

**Вопрос из зала ([21:39](https://youtu.be/h-7S6HNq0Vg?t=1299)):** нужно ли обучать embedding-модель? — **Ответ:** два варианта — взять предобученную (так обычно и делают) или обучить свою. Её назначение — представлять chunks так, чтобы хорошо находились релевантные документы; как такие модели обучают, будет дальше (SBERT).

### Два этапа retrieval

Методы взяты из рекомендательных систем и поиска ([23:35](https://youtu.be/h-7S6HNq0Vg?t=1415)); LLM-сообщество заимствовало их оттуда.

1. **Candidate retrieval** ([24:27](https://youtu.be/h-7S6HNq0Vg?t=1467)) — из очень большого множества chunks грубо отобрать небольшой набор потенциально релевантных. Цель — максимизировать recall: захватить как можно больше кандидатов, которые могут подойти.
2. **Ranking** — иногда опциональный этап: отсортировать кандидатов так, чтобы действительно релевантные оказались наверху. Здесь можно позволить себе более тяжёлую модель, потому что кандидатов уже мало.

Качество embeddings влияет в первую очередь на первый этап, но второй не менее важен.

**Вопрос из зала ([26:09](https://youtu.be/h-7S6HNq0Vg?t=1569)):** режем ли мы chunks наивно, просто по числу токенов? — **Ответ:** будут расширения, которые смягчают проблему бессмысленных границ (contextual retrieval). Кроме того, при нарезке нужно учитывать структуру файла — JSON, markdown и т. п.; в детали лекция не идёт.

> 💡 **Дополнение — на практике:** Плохой chunking — самая частая причина «RAG не работает»: таблица режется посередине, и строки теряют заголовки колонок; сигнатура функции попадает в один chunk, а её описание — в другой; местоимение «он» в начале chunk'а ссылается на сущность из предыдущего. Поэтому режут не по счётчику токенов, а по структуре — по заголовкам, абзацам, элементам списка, блокам кода — и лишь внутри слишком длинного элемента по токенам (так работают «рекурсивные» сплиттеры в популярных библиотеках). Полезно также вписывать в текст chunk'а его «адрес» — название документа и путь по заголовкам: тогда и embedding, и BM25 видят, откуда фрагмент, а модель может сослаться на источник.

## 3. Семантический поиск: SBERT и bi-encoders

⏱ 27:39–34:25 · [▶ смотреть на YouTube](https://youtu.be/h-7S6HNq0Vg?t=1659)

Первый этап — candidate retrieval: из потенциально огромной базы отобрать, скажем, около 100 кандидатов. Используются embeddings, посчитанные при построении knowledge base, и семантический поиск по близости. Запрос тоже превращается в embedding, для каждого chunk считается similarity score — почти всегда cosine similarity — и берётся top-100 (или сколько нужно):

$$\cos(\mathbf{q}, \mathbf{c}) = \frac{\mathbf{q}\cdot\mathbf{c}}{\|\mathbf{q}\|\,\|\mathbf{c}\|}$$

где $\mathbf{q}$ — embedding запроса, $\mathbf{c}$ — embedding chunk'а, в числителе их скалярное произведение, в знаменателе произведение длин векторов; значение 1 означает, что векторы сонаправлены.

**Сложность поиска** ([29:28](https://youtu.be/h-7S6HNq0Vg?t=1768)). База может быть огромной, поэтому вместо наивного линейного перебора применяют approximate nearest neighbor (ANN, приближённый поиск ближайших соседей): при построении базы embeddings заранее разбивают на разделы так, чтобы не сравнивать запрос со всеми. Есть готовые библиотеки; в детали лекция не идёт.

> 💡 **Дополнение — уточнение:** Названная лектором размерность «около 1 500» — это, по-видимому, 1536: столько измерений у распространённых embedding-моделей OpenAI (text-embedding-ada-002, text-embedding-3-small); у более крупных моделей бывает 3072 и больше. Из библиотек ANN чаще всего встречаются FAISS и индекс HNSW (граф ближайших соседей, по которому поиск идёт за логарифмическое время); те же индексы встроены в векторные базы вроде pgvector, Qdrant или Pinecone. Важная практическая деталь: запрос и chunks нужно кодировать одной и той же моделью одной и той же версии — embeddings разных моделей живут в разных пространствах и несравнимы, так что смена модели означает переиндексацию всей базы.

**Bi-encoder** ([30:19](https://youtu.be/h-7S6HNq0Vg?t=1819)). Embeddings получают, пропуская текст через модель — обычно encoder-only, BERT-подобную (BERT был на лекции 2–3). Архитектуру называют bi-encoder, потому что запрос и chunk проходят через encoder *независимо друг от друга*, и сравниваются уже готовые векторы.

**Sentence-BERT (SBERT)** ([31:11](https://youtu.be/h-7S6HNq0Vg?t=1871)) — статья, которую лектор настоятельно советует прочитать: расширение BERT, выдающее один embedding на последовательность (запрос, документ), специально приспособленный для similarity search. Функция потерь устроена так, чтобы у релевантных пар cosine similarity была высокой, а у нерелевантных — низкой. Зная BERT, статья читается легко.

**Вопрос из зала ([32:17](https://youtu.be/h-7S6HNq0Vg?t=1937)):** какая мера сходства по умолчанию? — **Ответ:** cosine similarity, но в реализациях встречаются и другие расстояния, например L2; если все векторы нормированы на 1, формулы сильно упрощаются, и варианты оказываются «более или менее косинусом». *Примечание:* для единичных векторов $\|\mathbf{q}-\mathbf{c}\|^2 = 2 - 2\cos(\mathbf{q},\mathbf{c})$, то есть ранжирование по L2 и по косинусу совпадает.

**Что значит «семантический»** ([33:12](https://youtu.be/h-7S6HNq0Vg?t=1992)): находятся документы с тем же смыслом, но совпадение ключевых слов никак не гарантируется — найденный chunk может не иметь ни одного общего слова с запросом.

## 4. Эвристический поиск: BM25

⏱ 34:25–37:54 · [▶ смотреть на YouTube](https://youtu.be/h-7S6HNq0Vg?t=2065)

Иногда нужно, чтобы результаты обязательно содержали слова из запроса. Для этого есть второй способ — BM25: эвристический relevance score, функция от пересечения слов запроса и документа.

Пример с плюшевыми мишками ([35:24](https://youtu.be/h-7S6HNq0Vg?t=2124)): два медведя, Cuddly и Huggy; запрос — «где Cuddly?». BM25 по построению вернёт документы, где встречается «Cuddly». Семантический поиск такой гарантии не даёт: Huggy и Cuddly семантически близки, и среди результатов могут оказаться документы про Huggy без слова «Cuddly».

| | Embedding-поиск (dense) | BM25 |
|---|---|---|
| На чём основан | Близость embeddings (cosine) | Пересечение ключевых слов |
| Что находит | Тот же смысл, даже без общих слов | Документы с теми же словами, что в запросе |
| Гарантия keyword match | Нет | Есть |

На практике ([36:20](https://youtu.be/h-7S6HNq0Vg?t=2180)) смотрят на свой use case и решают, нужна ли эвристическая составляющая в relevance score; многие используют гибрид — комбинацию embedding-поиска и BM25, что для части задач даёт более релевантные документы.

*Примечание:* формулу BM25 на лекции не давали; стандартный вид — $\text{BM25}(q,d)=\sum_{t\in q}\mathrm{IDF}(t)\cdot\frac{f(t,d)\,(k_1+1)}{f(t,d)+k_1\left(1-b+b\,\frac{|d|}{\text{avgdl}}\right)}$, где $f(t,d)$ — частота терма $t$ в документе $d$, $|d|$ — длина документа, $\text{avgdl}$ — средняя длина документа в коллекции, $\mathrm{IDF}(t)$ — обратная документная частота терма, $k_1$ и $b$ — настраиваемые константы.

> 💡 **Дополнение — на практике:** BM25 выигрывает у embeddings там, где важны редкие точные токены: коды ошибок (`ECONNRESET`), артикулы, имена функций, номера тикетов, версии. Embedding-модель видела такие строки редко и кладёт их «где-то рядом» с похожими, а BM25 находит именно их. Гибрид обычно собирают просто: два списка кандидатов (semantic и BM25) сливают через Reciprocal Rank Fusion — каждому документу начисляют $\sum 1/(k + \text{rank})$ по обоим спискам (типично $k = 60$) и сортируют по сумме; так не нужно калибровать несравнимые score'ы cosine и BM25. Полученный объединённый список и отдают на re-ranking.

## 5. HyDE и contextual retrieval

⏱ 37:54–41:00 · [▶ смотреть на YouTube](https://youtu.be/h-7S6HNq0Vg?t=2274)

**Несоответствие запроса и документов.** Запрос обычно короткий, часто это вопрос; содержимое базы — длинные предложения. Если кодировать то и другое одним encoder'ом, embeddings получаются не очень сопоставимыми: один — для вопроса, другой — для документа.

**HyDE** ([38:50](https://youtu.be/h-7S6HNq0Vg?t=2330)) смягчает это: вместо embedding промпта сначала одним LLM-вызовом генерируется «фальшивый» документ по промпту, и уже его embedding используется для поиска chunks. Работает не всегда, применяют не все; стоит попробовать и посмотреть. *Примечание:* HyDE расшифровывается как Hypothetical Document Embeddings. Альтернатива — отдельные encoders, специально обученные для запросов и для документов; так обычно не делают из соображений сопровождения.

**Contextual retrieval** ([39:53](https://youtu.be/h-7S6HNq0Vg?t=2393)) — ответ на вопрос о наивной нарезке. Chunk, вырванный из документа, может быть непонятен. Идея: к каждому chunk'у приписать короткий текст с контекстом, нужным для его понимания. Документ разбит на n chunks; вместо того чтобы рассматривать их по отдельности, для каждого вычисляют контекст на основе всего документа.

> 💡 **Дополнение — уточнение:** Описанная схема «контекст для каждого chunk'а по всему документу» — это метод Contextual Retrieval, который Anthropic описала в своём блоге осенью 2024 года; там контекст приписывается и к embeddings, и к BM25-индексу (contextual BM25), а дешевизна достигается именно prompt caching, о котором лектор говорит в следующем разделе: документ кладут в кэшируемый префикс, а меняется только chunk. По их данным гибрид с контекстом заметно снижает долю неудачных retrieval. А асимметрию «короткий вопрос против длинного документа» на практике решают не двумя encoders, а одним с подсказкой о типе входа: у многих embedding-моделей есть префиксы вроде `query:` / `passage:` или параметр `input_type` — модель обучена сближать вопрос и содержащий ответ фрагмент, а не два похожих текста.

## 6. Prompt caching

⏱ 41:00–45:24 · [▶ смотреть на YouTube](https://youtu.be/h-7S6HNq0Vg?t=2460)

Контекст для chunk'а получают ещё одним LLM-вызовом: модели дают весь документ и chunk и просят короткое, ёмкое описание, делающее chunk понятным. Chunks много — это много вызовов и дорого. Способ удешевить — prompt caching ([41:52](https://youtu.be/h-7S6HNq0Vg?t=2512)).

Логика: модели decoder-only работают слева направо, поэтому одинаковый префикс промпта даёт одинаковые вычисления. Вместо того чтобы считать их заново для каждого chunk'а, их делают один раз, сохраняют активации, а дальше просто берут из кэша (lookup) и декодируют остаток.

**Вопрос из зала ([41:52](https://youtu.be/h-7S6HNq0Vg?t=2512)):** что за активации? — **Ответ:** при подаче промпта модель вычисляет активации всех слоёв, и генерация делает attention поверх них; раз модель однонаправленная, одинаковый вход даёт одинаковые активации.

**Вопрос из зала ([42:59](https://youtu.be/h-7S6HNq0Vg?t=2579)):** а если модель закрытая? — **Ответ:** провайдеры закрытых моделей предлагают prompt caching как опцию: на странице с ценами есть цена за обычные входные токены и за кэшированные; у OpenAI кэшированный входной токен стоит 1/10 обычной цены ([43:56](https://youtu.be/h-7S6HNq0Vg?t=2636)).

Практический совет: собирать всё, что повторяется между промптами, в начало промпта, чтобы получать эту скидку.

> 💡 **Дополнение — на практике:** Кэшируется только *префикс*: провайдер сравнивает промпт с начала, и первое же отличие обнуляет кэш для всего, что ниже. Отсюда правила: описания инструментов и system prompt — наверх, а всё изменчивое (дата, имя пользователя, сам вопрос) — в конец; у некоторых API порядок фиксирован (tools → system → messages). У Anthropic точки кэширования ставятся явно (`cache_control`), у OpenAI кэш включается автоматически для промптов от ~1024 токенов. Чтение из кэша стоит около 10 % обычной цены за входной токен, но у Anthropic запись в кэш дороже базовой цены, а живёт кэш минуты — выгода есть только при серии вызовов подряд, что для contextual retrieval (один документ, сотни chunks) и для агентов (длинная история, много ходов) как раз выполняется. Технически это сохранение KV-кэша attention-слоёв — той же механики, что ускоряет декодирование (см. [Лекцию 3](03-llms-moe-decoding-prompting.md)).

Переход: первый этап сводит тысячи или миллионы chunks к сотням потенциально релевантных. Второй, опциональный, — отсортировать их осмысленнее и выбрать финальный top-k ([44:55](https://youtu.be/h-7S6HNq0Vg?t=2695)).

## 7. Re-ranking с cross-encoders

⏱ 45:24–47:49 · [▶ смотреть на YouTube](https://youtu.be/h-7S6HNq0Vg?t=2724)

Второй этап называют ranking или re-ranking — «re», потому что после первого этапа ранжирование уже есть. Вместо быстрой операции над готовыми embeddings используется более тяжёлая модель: запрос и chunk подаются в encoder *вместе*, и на выходе получается relevance score. Модель видит обе части одновременно и может уловить их взаимодействие, чего нет при сравнении двух независимых векторов.

| | Bi-encoder (этап 1) | Cross-encoder (этап 2) |
|---|---|---|
| Вход | Запрос и chunk кодируются по отдельности | Запрос и chunk в одном входе |
| Выход | Два embedding → cosine similarity | Один relevance score |
| Взаимодействие запрос–chunk | Нет | Есть — attention между запросом и chunk'ом |
| Стоимость | Дёшево: embeddings chunks считаются заранее | Дорого: считается для каждой пары на лету |
| Где применяется | Миллионы chunks → ~100 кандидатов | ~100 кандидатов → финальный top-k |

**Вопрос из зала ([46:27](https://youtu.be/h-7S6HNq0Vg?t=2787)):** то есть считается attention между запросом и chunk'ом? — **Ответ:** да, именно так.

Лектор рекомендует документацию Sentence Transformers (ссылка на слайде). Процедура проста: для каждого кандидата считается score с промптом, и получается итоговое ранжирование. Следующий вопрос — устраивает ли оно нас.

> 💡 **Дополнение — на практике:** Писать cross-encoder самому обычно не нужно: есть открытые модели (например, семейство bge-reranker и cross-encoder'ы ms-marco MiniLM из Sentence Transformers) и reranking как API (Cohere Rerank и аналоги у других провайдеров) — на вход список кандидатов и запрос, на выход score'ы. Цена — задержка: 100 пар через cross-encoder на CPU могут занимать заметную долю секунды, поэтому в чатах кандидатов часто режут до 20–50. Промежуточный вариант между bi- и cross-encoder — late interaction (ColBERT): токены запроса и документа кодируются отдельно, но сравниваются попарно, что дешевле cross-encoder и точнее одного вектора на текст. Наконец, reranker'ом может быть и сама LLM, которой показывают кандидатов и просят оценить релевантность — дорого, зато без отдельной модели.

## 8. Оценка retrieval: NDCG, MRR

⏱ 47:49–59:28 · [▶ смотреть на YouTube](https://youtu.be/h-7S6HNq0Vg?t=2869)

Чтобы ответить, нужно измерять качество; метрики те же, что в поиске и рекомендациях. Постановка: после двух этапов у нас есть k chunks наверху списка, которые мы называем релевантными, и есть ground truth — какие chunks релевантны на самом деле (метки, как в бинарной классификации). Для ранжирования важно ещё и *где* в списке стоят релевантные документы; в RAG интересуют только первые k, потому что именно они попадут в промпт.

### NDCG

NDCG ([49:37](https://youtu.be/h-7S6HNq0Vg?t=2977)) оценивает качество ранжирования с учётом позиций релевантных документов: чем ближе они к первому месту, тем выше score. Формула выглядит пугающе, но делает простую вещь:

$$\mathrm{DCG@}k = \sum_{i=1}^{k} \frac{rel_i}{\log_2(i+1)}, \qquad \mathrm{NDCG@}k = \frac{\mathrm{DCG@}k}{\mathrm{IDCG@}k}$$

- $k$ — число позиций, которые мы смотрим (сколько chunks идёт в промпт);
- $i$ — позиция в нашем ранжировании;
- $rel_i$ — релевантность chunk'а на позиции $i$: 1, если он действительно релевантен, иначе 0;
- знаменатель растёт с рангом — это *discount*: релевантный документ на первом месте даёт больше, чем на k-м (*Примечание:* лектор говорит лишь «некоторая функция ранга»; $\log_2(i+1)$ — стандартный выбор);
- *cumulative* — вклады суммируются по всем первым k позициям;
- $\mathrm{IDCG@}k$ — DCG идеального ранжирования для этого запроса (все релевантные документы наверху). Делить на него ([51:21](https://youtu.be/h-7S6HNq0Vg?t=3081)) нужно потому, что DCG сильно зависит от числа релевантных документов; после нормировки идеальное ранжирование даёт ровно 1, и score становится осмысленным и сравнимым между запросами.

**Вопрос из зала ([52:23](https://youtu.be/h-7S6HNq0Vg?t=3143)):** откуда берётся релевантность в формуле? — **Ответ:** два этапа дают score для каждого найденного chunk'а; по нему chunks сортируются по убыванию. А $rel_i$ — это реальная метка: смотрим на k найденных chunks и по ground truth проверяем, действительно ли релевантен первый, второй и т. д.

### MRR, precision@k, recall@k

- **Reciprocal rank** ([54:07](https://youtu.be/h-7S6HNq0Vg?t=3247)) — гораздо проще: обратная величина ранга первого релевантного документа. Если первый релевантный стоит на позиции 2, ранг равен 2 и $\mathrm{RR}=1/2$. Все релевантные документы ниже первого игнорируются. Метрика простая, но обычно хорошо коррелирует с NDCG, поэтому её используют. *Примечание:* MRR — среднее RR по набору запросов: $\mathrm{MRR}=\frac{1}{|Q|}\sum_{q\in Q}\frac{1}{\mathrm{rank}_q}$, где $Q$ — набор запросов, $\mathrm{rank}_q$ — позиция первого релевантного документа для запроса $q$.
- **Recall@k** ([54:59](https://youtu.be/h-7S6HNq0Vg?t=3299)) — ранжирующий аналог recall: из всех действительно релевантных документов (положительный класс) какая доля попала в top-k.
- **Precision@k** — из k выбранных документов какая доля действительно релевантна.

$$\text{Recall@}k=\frac{|\text{релевантные}\cap\text{top-}k|}{|\text{релевантные}|},\qquad \text{Precision@}k=\frac{|\text{релевантные}\cap\text{top-}k|}{k}$$

> 💡 **Дополнение — пример:** Пусть для запроса релевантны два chunk'а, а retriever вернул top-3 в порядке [релевантный, нерелевантный, релевантный]. Тогда $\mathrm{DCG@3} = 1/\log_2 2 + 0 + 1/\log_2 4 = 1 + 0.5 = 1.5$; идеальный порядок [релевантный, релевантный, нерелевантный] даёт $\mathrm{IDCG@3} = 1 + 1/\log_2 3 \approx 1.63$, и $\mathrm{NDCG@3} \approx 0.92$. Reciprocal rank равен 1 (первый же документ релевантен), precision@3 = 2/3, recall@3 = 2/2 = 1. Видно, что метрики отвечают на разные вопросы: RR — «быстро ли нашли хоть что-то», recall — «всё ли нужное попало в промпт», NDCG — «насколько хорош порядок».

Эти четыре метрики — NDCG, MRR, precision@k, recall@k — встречаются во множестве статей; лектор советует освоить их идею и формулы. Для сравнения retriever'ов есть популярный бенчмарк MTEB (Massive Text Embedding Benchmark, [56:47](https://youtu.be/h-7S6HNq0Vg?t=3407)): прогоняете свой retriever, получаете все метрики и сравниваете решения между собой.

**Вопрос из зала ([57:41](https://youtu.be/h-7S6HNq0Vg?t=3461)):** что за encoder на этапе re-ranking? — **Ответ:** модель, обученная выдавать relevance score; есть предобученные, можно сделать свою. Она сложнее модели первого этапа, потому что работает с ~100 кандидатами, а не с сотнями тысяч или миллионами, и на неё можно тратить больше времени.

**Вопрос из зала ([58:38](https://youtu.be/h-7S6HNq0Vg?t=3518)):** а обучение с contrastive loss? — **Ответ:** в лекции не разбирается; в статье SBERT сравниваются несколько функций потерь, contrastive — одна из них.

> 💡 **Дополнение — связь с лекцией 8:** Все четыре метрики оценивают только retriever и требуют размеченного набора «запрос → релевантные chunks». На практике его делают вручную для нескольких десятков типичных запросов или синтезируют: LLM генерирует вопросы к случайным chunks, и chunk-источник считается релевантным. Качество всего RAG-ответа измеряют отдельно, обычно через LLM-as-a-judge (faithfulness — опирается ли ответ на найденный контекст, answer relevance — отвечает ли он на вопрос; см. фреймворк RAGAS); как устроены такие оценки и чем они опасны — тема [Лекции 8](08-llm-evaluation.md).

На этом Afshine передаёт слово Shervine.

## 9. Tool calling

⏱ 59:28–1:26:22 · [▶ смотреть на YouTube](https://youtu.be/h-7S6HNq0Vg?t=3568)

### От неструктурированных данных к функциям

Shervine называет это своей любимой частью лекции. RAG — про неструктурированные данные, «документы из слов», из которых нужно выбрать релевантные. Tool calling — про *структурированные* данные: таблица с колонками, где выход определяется значениями входов. Такую связь естественно переписать как функцию с аргументами (ID, поле и т. д.) и возвращаемым значением — отсюда второе название, function calling. В примерах LLM обычно работают с Python, потому что он легко читается, но ничто не привязывает tool calling к конкретному языку.

Определение ([1:02:12](https://youtu.be/h-7S6HNq0Vg?t=3732)) лектор берёт из статьи IBM: tool calling позволяет автономным системам выполнять сложные задачи, динамически обращаясь к внешним ресурсам и действуя через них. Два ключевых момента: есть *задача*, которую нужно выполнить, и *возможная* (не обязательная) опора на внешние ресурсы — именно она закрывает пробел в знаниях модели, о котором говорил Afshine.

### Пример: «найди мне плюшевого мишку поблизости»

Вы в Stanford, достаёте телефон и просите LLM найти мишку рядом ([1:03:10](https://youtu.be/h-7S6HNq0Vg?t=3790)). Без инструментов модель не знает ничего о наличии мишек в реальном времени и ответит что-то вроде «не знаю». Цель раздела — понять, что положить в преамбулу (системную часть промпта) и через какие шаги пройти, чтобы запрос выполнился.

**Вопрос из зала ([1:04:09](https://youtu.be/h-7S6HNq0Vg?t=3849)):** эти API функций заданы заранее? — **Ответ:** да, они определяются заранее, а не генерируются моделью на лету.

Определение функции ([1:05:06](https://youtu.be/h-7S6HNq0Vg?t=3906)): `find_teddy_bear`, которая по локации вызывает некий API и возвращает кандидатов. Что в ней важно:
- **Документация** входа и выхода (docstring под функцией) — критична: по ней модель понимает, для чего функция.
- **Backend-вызов** — обращение к внешнему API за доступными мишками с фильтром по близости.
- **Структурированный выход** — класс, описывающий результат; именно на него модель будет опираться при финальном ответе.
- Модель **не видит реализацию** ([1:07:47](https://youtu.be/h-7S6HNq0Vg?t=4067)): ей доступны только сигнатура (API), вход/выход и основные строки документации. Код живёт в вашей кодовой базе.

### Три стадии вызова инструмента

1. **Предсказание аргументов.** В начало преамбулы вставляется API функции без реализации, с полной документацией. Задача модели — не угадать реализацию, а подобрать правильные аргументы к пользовательскому запросу. В примере координаты Stanford модель берёт из контекста: разрешение на геолокацию включено, и местоположение ей известно ([1:09:33](https://youtu.be/h-7S6HNq0Vg?t=4173)).
2. **Выполнение вызова.** К LLM отношения не имеет: берутся функция и аргументы, код исполняется, возвращается структурированный объект (имя мишки, локация и т. д.).
3. **Финальный ответ.** Результат подаётся обратно модели, чтобы она ответила пользователю естественным языком, а не JSON-подобной структурой.

> 💡 **Дополнение — пример:** В LLM API «преамбула с API функции» — это параметр `tools`, а docstring превращается в поле `description` плюс JSON Schema аргументов. Для мишки это выглядело бы так: `{"name": "find_teddy_bear", "description": "Находит плюшевых мишек рядом с заданной точкой", "input_schema": {"type": "object", "properties": {"lat": {"type": "number"}, "lon": {"type": "number"}, "radius_km": {"type": "number", "description": "Радиус поиска, км"}}, "required": ["lat", "lon"]}}` (имя поля со схемой отличается у провайдеров: `input_schema` у Anthropic, `parameters` у OpenAI). Три стадии лектора в API видны буквально: модель отвечает не текстом, а структурированным блоком вызова с именем функции и JSON аргументов (стадия 1); ваш код выполняет функцию и отправляет результат обратно сообщением типа «tool result» (стадия 2); модель пишет финальный ответ (стадия 3). Качество поля `description` — главный рычаг: именно по нему модель решает, когда звать инструмент и что класть в аргументы.

### Как этому научить: SFT

**Вопрос из зала ([1:08:37](https://youtu.be/h-7S6HNq0Vg?t=4117)):** как вообще такое обучать? — **Ответ:** разбирается с [1:11:20](https://youtu.be/h-7S6HNq0Vg?t=4280). Лектор спрашивает аудиторию, какие этапы требуют обучения, и приходит к двум типам SFT-пар:

- **Tool prediction**: вход — API функции и запрос пользователя; выход — вызов функции с аргументами. Модель должна распознавать связь между описанием функции и запросом.
- **Финальный ответ**: вход — вся история разговора (исходный запрос, факт вызова инструмента, его результат), выход — ответ в нужном формате. Казалось бы, модель и так умеет пересказывать структурированные данные словами, но обычно хочется конкретного формата ответа, поэтому такие пары тоже нужны; вход у них длиннее, чем просто JSON.

Примеров должно быть много, и они должны покрывать реальное распределение пользователей ([1:14:11](https://youtu.be/h-7S6HNq0Vg?t=4451)): «найди мишку рядом» учит брать локацию из контекста пользователя; «хочу мишку в таком-то месте» — брать её из запроса; плюс варианты формулировок и multi-turn, когда просьба возникает посреди разговора.

**Вопрос из зала ([1:13:18](https://youtu.be/h-7S6HNq0Vg?t=4398)):** а если инструментов много — нужен tool selection или просто больше примеров? — **Ответ:** в SFT можно показывать входы с несколькими инструментами; tool selection — отдельная тема чуть позже.

### Как обойтись без SFT: объяснение в промпте

Современные LLM хорошо рассуждают и на pre-training и instruction tuning видели много кода, то есть Python они уже умеют. Так ли нужно учить модель отображать запрос в вызов функции ([1:15:05](https://youtu.be/h-7S6HNq0Vg?t=4505))? Всё чаще SFT заменяют *объяснением* в промпте. Аудитория предлагает два пути ([1:16:54](https://youtu.be/h-7S6HNq0Vg?t=4614)):

- **Few-shot learning** — показать в контексте примеры вход/выход. Принятая практика, но с обобщением проблемы: конкретные примеры подгоняют модель под частные случаи, а не под всё многообразие языка.
- **Попросить модель рассуждать** — написать инструкцию, объясняющую логику. Но писать такой промпт руками очень трудно.

Практический приём ([1:17:44](https://youtu.be/h-7S6HNq0Vg?t=4664)): те же SFT-пары использовать как evaluation set — «на такой вопрос хочу такой вызов». Текущее объяснение прогоняется по набору, получаются победы и поражения по каждому примеру (скажем, «найди мишку в Париже» не работает). Этот список со score отдаётся reasoning-модели с вопросом: что изменить в объяснении, чтобы результаты стали лучше? Так объяснение итеративно улучшается, и на практике модель справляется с этим удивительно хорошо. Вывод лектора: не писать объяснение end-to-end самому — набросать черновик и отдать доработку сильной модели с хорошим знанием логики.

**Вопрос из зала ([1:19:35](https://youtu.be/h-7S6HNq0Vg?t=4775)):** это обучение или inference? — **Ответ:** обучение, офлайн: итерации идут в самом начале, пока не получится фиксированный промпт. На inference этот фиксированный текст кладётся рядом с API функции, и модель знает, что делать с любым запросом.

> 💡 **Дополнение — связь с лекцией 5:** Два типа SFT-пар — это обычные данные instruction tuning из [Лекции 5](05-llm-tuning-rlhf-dpo.md), только с вызовом функции в роли «ответа»; провайдеры уже прогнали такое обучение, поэтому разработчик на API никогда не делает SFT под свои инструменты — он идёт «путём объяснения»: поле `description`, system prompt и при необходимости пара примеров. У ряда провайдеров есть strict-режим, гарантирующий, что аргументы вызова соответствуют JSON Schema, так что ошибки формата отпадают и остаются только смысловые. А цикл «eval-набор → прогон → reasoning-модель переписывает инструкцию» — это в чистом виде automatic prompt optimization; если нужен готовый инструментарий, искать по DSPy и его оптимизаторам промптов.

### Категории инструментов

([1:20:28](https://youtu.be/h-7S6HNq0Vg?t=4828))
- **Информационные** — пример с мишкой; новости дня через инструмент Search (обход knowledge cutoff), погода, котировки.
- **Вычислительные** — вместо цепочки рассуждений модель переводит запрос в код, код исполняется, ответ читается обратно.
- **Действия от имени пользователя** — инструмент отправки email: модель заполняет заголовок и тело и может нажать «отправить», поскольку компонент, взаимодействующий с внешним миром, — часть API инструмента.

### Много инструментов и итог раздела

На практике в контексте не один API, а несколько: обнять мишку, проверить его настроение, отправить подарок... Все кладут в преамбулу «на всякий случай», так как заранее неизвестно, что понадобится. Студент замечает ([1:23:11](https://youtu.be/h-7S6HNq0Vg?t=4991)): это очень много инструментов. Верно — возникает та же needle-in-a-haystack проблема: API теряются в контексте, конфликтуют между собой.

Итог ([1:24:11](https://youtu.be/h-7S6HNq0Vg?t=5051)): от LLM, которая просто отвечала словами, мы пришли к LLM, которая взаимодействует с внешним миром, получает информацию в реальном времени и расширяет вычислительные возможности. Knowledge cutoff закрывается иначе, чем в RAG, — два метода дополняют друг друга. Три недостатка:
1. Чем больше инструментов, тем больше лишнего в контексте; пытаясь поддержать всё, рискуешь стать посредственным во всём.
2. Контекст конечен: при сотнях миллионов пользователей с разными задачами все инструменты в него не поместятся.
3. Инструменты написаны руками, и у каждой LLM свой формат их описания — нужна стандартизация.

## 10. Tool selection

⏱ 1:26:22–1:29:17 · [▶ смотреть на YouTube](https://youtu.be/h-7S6HNq0Vg?t=5182)

Как сделать tool use масштабируемым. Лектор ссылается на технический отчёт Google DeepMind с системой tool selector, работающей в два шага:

1. Модели дают запрос и список инструментов — сколь угодно длинный, но в нём каждый инструмент представлен только именем API и парой слов о назначении. Модель выбирает те, что могут пригодиться.
2. В контекст вместе с запросом подаются полные API только выбранных инструментов.

В литературе то же называют router; tool selection и routing — близкие понятия. Цель — ограничить набор инструментов теми, что могут быть полезны.

**Вопрос из зала ([1:28:14](https://youtu.be/h-7S6HNq0Vg?t=5294)):** это же по сути RAG? — **Ответ:** можно сделать и через RAG, но не обязательно: выбор может делать сама LLM по инструкции.

Переход к стандартизации ([1:29:04](https://youtu.be/h-7S6HNq0Vg?t=5344)): описание инструмента может быть специфичным для конкретной LLM, и тогда одни и те же инструменты придётся реализовывать заново для каждой модели — дублирование, которого никто не хочет.

## 11. Model Context Protocol (MCP)

⏱ 1:29:17–1:31:56 · [▶ смотреть на YouTube](https://youtu.be/h-7S6HNq0Vg?t=5357)

MCP (Model Context Protocol) — стандарт от Anthropic, задающий единый способ предъявлять инструменты моделям. Лектор даёт только «крупными мазками» словарь протокола:

| Понятие | Что это |
|---|---|
| MCP server | Инстанс, который предоставляет инструменты |
| Tools | Реализации функций, которыми должны пользоваться модели |
| Prompts | Шаблоны, показывающие, как использовать инструменты |
| Resources | Внешние базы данных, на которые опираются инструменты и промпты |
| MCP client | Компонент в LLM-хосте, с которым сервер связан один-к-одному (инфраструктурная деталь) |

Пример ([1:30:59](https://youtu.be/h-7S6HNq0Vg?t=5459)): мишка любит поэзию, нужно порекомендовать ему книгу. LLM-хост — Claude (раз уж MCP от Anthropic). MCP server реализует продавец книг — он лучше всех умеет отдавать такой контент. Его tools — поиск и рекомендация книг; prompts — как найти конкретное название или подобрать книгу под вкус пользователя; resources — личная коллекция мишки или список самых покупаемых книг.

> 💡 **Дополнение — уточнение:** Сама модель «не говорит на MCP»: протокол (JSON-RPC поверх stdio или HTTP, методы вроде `tools/list` и `tools/call`) связывает MCP client в хост-приложении — IDE, десктопном клиенте, вашем агенте — с сервером, а хост уже переводит полученный список инструментов в обычный параметр `tools` для LLM API из предыдущих разделов. То есть MCP стандартизирует интеграцию, а не формат, который видит модель. Два практических следствия: каждый подключённый сервер добавляет в контекст десятки описаний, и проблема «слишком много инструментов» из раздела про tool selection наступает быстро — по состоянию на 2026 год провайдеры и фреймворки отвечают на это отложенной загрузкой схем (модель видит только имена и подгружает полное описание по запросу, то есть ровно двухшаговый tool selector из лекции); а описания инструментов стороннего сервера — недоверенный текст, который попадает в промпт, со всеми рисками из раздела о безопасности.

## 12. Агенты и ReAct

⏱ 1:31:56–1:42:16 · [▶ смотреть на YouTube](https://youtu.be/h-7S6HNq0Vg?t=5516)

### Определение

Агент — «уровень выше» инструментов: система, которая автономно преследует цель и выполняет задачи от имени пользователя. В отличие от инструмента здесь есть рассуждение и несколько итераций — цикл. Именно рекуррентность и более высокий уровень рассуждений отличают агента от инструмента. Агентный framework не отделён от уже виденного: внутри могут быть цепочки рассуждений из прошлой лекции, а структура состоит из вызовов инструментов и итераций.

### ReAct

Знаковая статья ReAct (Reason + Act, [1:33:41](https://youtu.be/h-7S6HNq0Vg?t=5621)): цель часто нельзя достичь за один шаг; её нужно разложить на атомарные подшаги, выполнить каждый и собрать ответ. На лекции цикл описан стадиями observe → plan → act; в самой статье ReAct, по словам лектора, термины другие (think, observe, act), и от статьи к статье названия меняются, но интуиция одна.

### Пример: «моему мишке холодно, сделай что-нибудь»

([1:34:31](https://youtu.be/h-7S6HNq0Vg?t=5671))

| Итерация | Стадия | Что происходит |
|---|---|---|
| 1 | Observe | Запрос переводится в рабочую формулировку: мишке холодно → возможно, дело в температуре комнаты, которая пока неизвестна |
| 1 | Plan | Нужно узнать температуру комнаты |
| 1 | Act | Среди инструментов есть `get_current_room_temperature` — вызываем, получаем значение |
| 2 | Observe | В комнате 65 °F — холоднее, чем ожидалось |
| 2 | Plan | Нужно поднять температуру |
| 2 | Act | Вызываем функцию с аргументом «на сколько поднять» |
| 3 | Observe | Температура выставлена правильно → цель достигнута, выход из цикла |
| — | Output | Пользователю: «температура поднята на 5 градусов» |

Именно этот цикл делает workflow агентным: есть исходный запрос, набор доступных действий, и на каждой стадии модель проверяет, достигнута ли цель. Если да — переходит к выводу, если нет — делает ещё круг рассуждений и действий ([1:37:58](https://youtu.be/h-7S6HNq0Vg?t=5878)).

> 💡 **Дополнение — на практике:** В реальном агентном цикле ломаются предсказуемые места: модель зацикливается, вызывая один и тот же инструмент с теми же аргументами; «галлюцинирует» результат инструмента, не вызвав его; объявляет цель достигнутой раньше времени (в примере — отчитывается о +5 градусах, не вызвав термостат); или накапливает в истории столько результатов, что начинает терять инструкции. Стандартные предохранители: лимит итераций и бюджет токенов, возврат ошибок инструмента текстом (чтобы модель могла исправиться, а не упасть), проверка, что перед словом «сделано» действительно был вызов, и обязательный лог каждого шага — те самые цепочки рассуждений, которые лектор советует читать при отладке. Reasoning-модели из [Лекции 6](06-llm-reasoning.md) встраиваются в этот цикл естественно: стадии observe и plan становятся их скрытой цепочкой рассуждений перед каждым вызовом.

### Несколько агентов и Agent2Agent

Можно пойти дальше: агент для термостата, агент для распределения энергии, агент для качества воздуха. Пользователь говорит одному агенту, а агенты общаются между собой — для этого нужна стандартизация общения агентов, как MCP стандартизировал общение хоста с инструментами. Так в этом году появился протокол Agent2Agent от Google ([1:39:50](https://youtu.be/h-7S6HNq0Vg?t=5990)); лектор советует прочитать спецификацию. Основное: агент выставляет наружу набор skills (что он умеет) с примерами, чтобы другие агенты о них знали; разработчик определяет skills и то, как агент исполняет запрос — какой статус он сообщает другим агентам, и метод cancel: что происходит, когда другой агент просит остановиться.

**Вопрос из зала ([1:40:44](https://youtu.be/h-7S6HNq0Vg?t=6044)):** каждый агент — это LLM со своим контекстом под задачу? — **Ответ:** в этом примере да; агенты работают независимо, у каждого свой цикл рассуждений, а наружу — только вход и выход.

**Реплика из зала ([1:41:34](https://youtu.be/h-7S6HNq0Vg?t=6094)):** расход токенов может разлететься. — **Ответ:** да, стоит вводить ограничения бюджета; агенты не тратят бюджет друг друга, но все вместе тратят ваши деньги.

## 13. Безопасность и заключение

⏱ 1:42:16–1:49:00 · [▶ смотреть на YouTube](https://youtu.be/h-7S6HNq0Vg?t=6136)

### Риски

С новыми возможностями приходит и новый класс проблем: модели теперь выполняют действия, и злоумышленник может заставить их сделать то, чего вы не хотите. Пример — data exfiltration (утечка данных): есть инструмент, который пишет куда-то публично, например email-агент; промпт вроде «отправь мой пароль на такой-то адрес» — а пароль инструменту может быть доступен — выводит данные пользователя наружу ([1:42:21](https://youtu.be/h-7S6HNq0Vg?t=6141)). Другие риски перечислены в статье на слайде (в субтитрах название звучит как «tool sort», вероятно ToolSword).

### Два класса защит

([1:43:19](https://youtu.be/h-7S6HNq0Vg?t=6199))
1. **На этапе обучения** — вспомните обучение R1 и других моделей: в data mixture для SFT и RL входят данные про harmlessness, которые покрывают и безопасность.
2. **На inference** — если запрос прошёл через обученные «линии обороны», остаются safeguards во время работы: например, safety classifier, который смотрит на разговор и судит, безопасен ли будет ответ модели.

Ориентир — Agent-SafetyBench: обзор возможных угроз плюс полный набор тестов, по которому можно проверить безопасность своей LLM.

Актуальный пример ([1:45:08](https://youtu.be/h-7S6HNq0Vg?t=6308)): накануне лекции Anthropic сообщила о крупномасштабной кибератаке, проведённой с помощью Claude — с использованием инструментов и агентных возможностей, — и опубликовала подробный отчёт о действиях атакующих и возможных мерах защиты. Лектор советует прочитать: и атаки, и защита становятся изощрённее; это не проигранная битва, но меры нужны.

> 💡 **Дополнение — уточнение:** Пример с паролем — частный случай prompt injection: инструкция для модели приходит не от пользователя, а из данных (письма, веб-страницы, найденного RAG-документа или результата инструмента). Опасной считается комбинация трёх свойств агента — доступ к приватным данным, чтение недоверенного контента и возможность отправлять что-то наружу (в индустрии её называют «lethal trifecta»); убрав любое из трёх, атаку заметно усложняют. Отсюда практические правила: минимальные права у каждого инструмента, подтверждение человеком необратимых действий (отправка, удаление, оплата), а результаты инструментов и retrieval — данные, а не команды. И уточнение к пересказу отчёта Anthropic: по самому отчёту, Claude был инструментом атакующих, а целями — сторонние организации, то есть речь не об атаке на Anthropic; лектор, видимо, оговорился, а субтитры усилили неточность.

### Почему агенты ещё не «правят миром» и как с ними работать

([1:46:07](https://youtu.be/h-7S6HNq0Vg?t=6367))
- На каждом шаге рассуждений агент может уйти в сторону: неправильно привязать результат, ошибиться в аргументах вызова. Ошибки накапливаются — поэтому крупномасштабных агентов пока нет.
- Такие пробелы можно закрывать через SFT, но лучше полагаться на возможности самой модели; как оценивать модели — тема следующей лекции.
- Советы по разработке инструментов и агентов ([1:47:01](https://youtu.be/h-7S6HNq0Vg?t=6421)): начинать с маленького простого случая («найди ближайшего мишку») и убедиться, что реализация и промпты работают; брать сначала самую способную модель, чтобы понимать потолок возможного, и лишь потом оптимизировать задержку и прочее — «start small and then start smart»; для отладки читать цепочки рассуждений модели.
- Любимое применение агентов у лектора — AI-ассистент для кодинга: снимает умственную нагрузку при сложной «обвязке». Но учите основы и умейте писать код правильно, потому что теперь главное — ваш вкус: «generating code is cheap», а оценить, корректен ли код и делает ли он то, что нужно, — трудная часть ([1:48:44](https://youtu.be/h-7S6HNq0Vg?t=6524)).

## Ключевые термины

| Термин | Что это (как объясняли на лекции) |
|---|---|
| Knowledge cutoff | Дата, до которой собраны обучающие данные; о более поздних событиях базовая модель не знает (GPT-5: 30 сентября 2024) |
| Needle in a haystack | Тест: в длинный промпт прячут факт и спрашивают о нём; с ростом длины и при факте в первой половине промпта модель его теряет |
| RAG | Retrieval Augmented Generation: retrieve релевантные документы → augment промпт → generate ответ |
| Chunk / knowledge base | Фрагмент документа ограниченной длины (около 500 токенов) с перекрытием соседних в низкие сотни токенов; knowledge base — все chunks с их embeddings |
| Embedding | Векторное представление chunk'а или запроса (размерность порядка тысяч, например 1 500), по которому ищут похожее |
| Candidate retrieval | Первый этап retrieval: быстро отобрать ~100 кандидатов из миллионов chunks, максимизируя recall |
| Ranking / re-ranking | Второй, опциональный этап: более тяжёлой моделью отсортировать кандидатов и выбрать top-k |
| Cosine similarity | Стандартная мера близости embeddings; L2 при единичных нормах сводится к ней |
| ANN | Approximate nearest neighbor: разбиение embeddings при построении базы, чтобы не делать линейный перебор |
| Bi-encoder | Запрос и chunk кодируются независимо, сравниваются готовые векторы; архитектура первого этапа |
| SBERT | Sentence-BERT: расширение BERT, дающее embedding на последовательность; loss тянет cosine similarity релевантных пар вверх, нерелевантных — вниз |
| Cross-encoder | Запрос и chunk подаются в encoder вместе, attention между ними, на выходе relevance score; архитектура re-ranking |
| BM25 | Эвристический relevance score по пересечению слов запроса и документа; гарантирует keyword match; часто в гибриде с embedding-поиском |
| HyDE | По промпту LLM генерирует «фальшивый» документ, и ищут по его embedding, чтобы сблизить природу запроса и документов |
| Contextual retrieval | К каждому chunk'у LLM-вызовом приписывается короткий контекст, вычисленный по всему документу |
| Prompt caching | Активации для общего префикса промпта считаются один раз и переиспользуются; у провайдеров кэшированные токены дешевле (OpenAI — 1/10) |
| NDCG | Normalized discounted cumulative gain: сумма релевантностей первых k позиций с убывающим по рангу весом, делённая на идеальный DCG |
| MRR | Обратная величина ранга первого релевантного документа (усреднённая по запросам); проще NDCG, хорошо коррелирует |
| Precision@k / Recall@k | Доля релевантных среди top-k / доля всех релевантных, попавших в top-k |
| MTEB | Massive Text Embedding Benchmark — популярный бенчмарк для сравнения retriever'ов |
| Tool calling / function calling | Модель получает API функции с документацией, предсказывает аргументы; код выполняет вызов; результат возвращается модели для ответа |
| Tool selection / router | Отдельный шаг, на котором по краткому списку инструментов модель выбирает нужные, и только их API идут в контекст |
| MCP | Model Context Protocol (Anthropic): стандарт предъявления инструментов моделям — server, tools, prompts, resources, client |
| Agent | Система, автономно преследующая цель от имени пользователя: вызовы инструментов плюс рассуждение в цикле |
| ReAct | Reason + Act: разложение задачи на цикл атомарных шагов observe → plan → act до достижения цели |

## Главные выводы

- Знания модели заканчиваются на дате cutoff. Дообучение (регрессии, переобучение всех fine-tune'ов) и «всё в контекст» (лимит окна, needle-in-a-haystack, цена за токены) не работают — RAG добавляет в промпт только релевантное.
- Качество RAG — это качество retrieval. Он двухэтапный: дешёвый отбор кандидатов на recall (bi-encoder, cosine similarity, ANN), затем дорогое ранжирование ~100 кандидатов cross-encoder'ом.
- Семантический поиск не гарантирует совпадения ключевых слов; если оно нужно, добавляйте BM25 и делайте гибрид под свой use case.
- Помните о несоответствии запроса и документов (HyDE, раздельные encoders) и о вырванных из контекста chunks (contextual retrieval); массовые LLM-вызовы удешевляйте prompt caching — всё повторяющееся в начало промпта.
- Retriever нужно измерять: NDCG, MRR, precision@k, recall@k, бенчмарк MTEB.
- При tool calling модель видит только API и документацию функции и предсказывает аргументы; выполнение происходит вне модели, результат возвращается ей для ответа. API задаются заранее.
- Учить вызову инструментов можно SFT (пары «запрос → вызов» и «история → ответ») или объяснением в промпте, которое итеративно улучшает reasoning-модель по eval-набору; руками такой промпт не пишут.
- Много инструментов → tool selection (router); разные форматы инструментов → MCP; многошаговые задачи → агенты с циклом observe/plan/act (ReAct); общение агентов → Agent2Agent.
- Агенты выполняют действия, поэтому безопасность критична: защита в данных SFT/RL, safety classifier на inference, Agent-SafetyBench; отчёт Anthropic о кибератаке — свежее напоминание.
- Начинайте с малого и с самой сильной модели, читайте цепочки рассуждений при отладке; генерировать код дёшево, судить о его корректности — трудно, и именно это теперь главный навык.

## Чем можно дополнить

- **Переписывание и декомпозиция запроса.** Лекция берёт пользовательский запрос как есть; на практике перед retrieval его часто переформулируют (несколько вариантов запроса, более общий «step-back» вопрос) или разбивают на подвопросы для multi-hop задач, где ответ собирается из нескольких документов. Искать: query rewriting, multi-query retrieval, step-back prompting, Self-RAG.
- **Graph RAG.** Вместо плоского списка chunks — граф сущностей и связей, извлечённый LLM из документов, с ответами по сообществам графа; помогает на вопросах «обо всём корпусе», где семантический поиск по chunks бессилен. Искать: GraphRAG (Microsoft).
- **Обученный разреженный и late-interaction retrieval.** Между BM25 и dense embeddings есть модели, которые учат веса терминов (SPLADE) или сравнивают токены попарно (ColBERT); они закрывают часть слабостей обоих подходов из лекции. Искать: SPLADE, ColBERT, learned sparse retrieval.
- **Оценка RAG целиком и оценка агентов.** В лекции метрики только для retriever; для ответов нужны faithfulness / groundedness и LLM-as-a-judge ([Лекция 8](08-llm-evaluation.md)), а для tool calling и агентов — свои бенчмарки. Искать: RAGAS, Berkeley Function Calling Leaderboard (BFCL), τ-bench, SWE-bench, GAIA.
- **Паттерны построения агентов.** Лекция даёт один цикл ReAct; в инженерной практике различают детерминированные workflow (цепочка, маршрутизация, параллелизация, orchestrator–workers, evaluator–optimizer) и «настоящих» агентов — и советуют начинать с первых. Искать: «Building effective agents» (Anthropic, 2024), planner–executor, reflection.
- **Память и управление контекстом агента.** Долгие сессии упираются в окно контекста: нужны сжатие истории (compaction), вынос фактов в долговременную память и подгрузка их через тот же retrieval. Искать: context engineering, agent memory, compaction.
- **Prompt injection и безопасность инструментов глубже.** Лекция даёт один пример и два класса защит; стоит знать таксономию indirect prompt injection, песочницы для выполнения кода, разграничение прав и human-in-the-loop. Искать: indirect prompt injection, lethal trifecta, AgentDojo, sandboxing для code execution.
- **Обучение моделей пользоваться инструментами.** Лекция описывает SFT-пары абстрактно; классические работы показывают, как модель сама учится вставлять вызовы API в текст и как собирают такие данные. Искать: Toolformer, Gorilla, ToolBench.
